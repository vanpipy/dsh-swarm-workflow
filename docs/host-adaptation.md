# Host adaptation — the shipped text, adapted to DeepSeek Harness

The three shipped policy files are the user's own text:

- `prompt-overlay.md` — the global execution policy
- `swarm-prompt.md` — the delegation briefing
- `skills/swarm-engineering/swarm-engineering.md` — the role methods

Their canonical copies live in `D:\project\lazible-jcode\config`. The bundle is
a carrier, not an author: the canonical text is the source, and this file
records the passages where the bundle deliberately diverges from it.

## Why the text diverges

The shipped text names the surfaces of the host it ships on. On the canonical
runtime those surfaces are the `swarm` tool, its `spawn` and `launch` actions,
`swarm await_members`, `swarm list`, `swarm message`, `swarm stop`,
`swarm summary`, the `[agents] swarm_*` settings, the `/autoreview` and
`/autojudge` commands, the `~/.jcode` override paths and the Jcode CLI. This
host is DeepSeek Harness, and none of those exist here: a lane that reads
`swarm list` has nothing to run.

So the text is adapted, and the adaptation is deliberate rather than silent:

- the rule the passage carried is kept;
- the surface that replaces it on this host is named in the passage itself;
- the passage is listed below with the reason it changed.

Everything else stays byte-identical to the canonical. Where a surface has no
counterpart here, the passage says so and keeps the rule.

## What is not adapted

- The nine craft files under `skills/swarm-engineering/` are host-neutral: they
  carry the method, not a runtime surface, so they are compared through the
  documented port transform rather than adapted.
- `runtime-note.md` is the plugin's own file: it holds every host fact, and
  the surface map in it records what each canonical surface became.
- `index.js` composes the views; it does not rewrite the shipped text at
  composition time.

## How the divergence is guarded

The checker ships inside this bundle, at `tools/check-policy-sync.ps1`, so a
fresh clone can check itself:

```
npm run check:policy                 # the bundle against the canonical
node tools/check-policy.mjs --self   # the bundle half only, no canonical
```

The bundle path is derived from the script's own location. The canonical
repository is the `-Canonical` parameter, then `$env:SWARM_POLICY_CANONICAL`,
then the `canonicalRepo` field of the record. The canonical side is always
read at the revision the record pins (`canonicalCommit`, written from
`git rev-parse HEAD` when the record is refreshed), so a canonical that has
moved is reported as its own failure instead of quietly changing the
comparison. The canonical's **working tree** is reported next to it: a
canonical whose tracked files have moved away from the pinned revision is its
own failure (`the canonical working tree`), stated separately from the
revision check, because the comparison itself is still made at the pinned
revision and stays sound. The canonical's working tree is reported next to the pinned
revision: a working tree that has moved away from that revision is its own
failure too, because the record was written against the revision and not
against whatever the tree happens to hold now. The canonical's working tree is reported beside that revision: a
canonical whose tracked files have been edited away from the pinned revision
is a failure of its own, named `the canonical working tree`, and it is
compared with git rather than with bytes, because a Windows checkout carries
CRLF where the pinned blob carries LF and that difference is not a change.

The guard prints what it did in three counts, so a reader can tell a clean
comparison from a comparison that never happened:

- `passed` — the comparison was made and agreed;
- `failed` — the comparison was made and disagreed (drift, a stale hash, a
  fabricated surface, a file that could not be read);
- `not comparable` — the two sides could not be put side by side (a missing
  canonical, a canonical that is not a git repository, a section the pinned
  revision does not have);
- `skipped` — the comparison belongs to a mode that does not make it (`--self`
  leaves the canonical half out), and a required comparison that could not be
  made is counted here as well, never as passed.

Its exit codes are: `0` — every comparison was made and every one agreed;
`1` — something drifted, failed, or a comparison could not be made; `2` — the
guard could not run at all: an argument it does not know, no PowerShell to run
it with, or no bundle tree to compare. The last line states the verdict in
words (`RESULT: CLEAN` or `RESULT: NOT CLEAN`), so a run that ends in `1` is
never read as a clean one.

It compares the three shipped files **section by section** against the
canonical, using the record in `docs/host-adaptation.json`:

- a section nobody adapted must be byte-identical to the canonical;
- an adapted section must be listed, with both hashes and a reason;
- an unrecorded difference, a hash that is out of date, an entry with no
  reason and a record that lists a section which no longer differs all fail;
- a heading that was renamed is recorded with its canonical wording in
  `canonicalHeading`, so a deliberate rename is an adaptation and not a
  structural difference;
- the `surfaces` column holds the host surfaces the passage names: a listed
  surface must occur in the passage or in the reason, and a surface the
  passage names must be listed.

`-Mode Refresh` rewrites `docs/host-adaptation.json` and regenerates the table
above; it keeps the reasons that are already written, so a refresh never
launders an unreviewed change into the record. `-Mode Emit` prints the stored
and the derived `surfaces` column of every row.

The exit code says what kind of outcome the run had: **0** when every
comparison the run made agreed, **1** when something drifted, failed, or a
comparison could not be made at all, and **2** when the guard could not run —
an argument it does not know, no PowerShell to run it with, or no bundle tree
to compare. A comparison that could not be made is counted as *skipped* and
as *blocking*, never as passed, so a missing canonical repository cannot be
mistaken for a clean run: the summary names the split
(`0 drifted, 0 not comparable, 0 skipped`) and the last line states the
verdict (`RESULT: CLEAN` or `RESULT: NOT CLEAN`). A bundle file that cannot be
read is a failure, not a gap — a file the checker never saw is a file nobody
compared.

The nine craft files are compared through the same checker with the documented
port transform, and the result is reported separately from the policy files.
